## Resumen ejecutivo

El sistema está **notablemente más sano que en la auditoría anterior**: el hallazgo
crítico de liquidez está cerrado, la deuda de lint bajó de 166 a 7 errores, y la
calibración del insider signal y la frescura del short interest se corrigieron.

Queda **un problema estructural**: la superficie completa de señales de trading es
pública. 37 de 59 rutas API no exigen autenticación, incluido `/api/scanner-pro`,
que además puede forzar un fallback de ~100 s contra Yahoo sin límite de tasa.

De 13 candidatos investigados, **8 se confirmaron** y **5 se descartaron** tras
verificación adversarial (documentados abajo — el descarte también es resultado).

## Hallazgos

### 🟠 ALTO

#### 1. La superficie de señales de trading es pública — 37 de 59 rutas sin auth

**CONFIRMADO** (estático + runtime)

`proxy.ts:40` excluye `/api` del matcher a propósito: cada handler debe aplicar su
propia auth. Solo 19 lo hacen. Auditadas las 59 rutas resolviendo delegaciones:

| Mecanismo | Rutas |
|---|---|
| JWT de sesión | `alerts`, `portfolio`, `portfolios`, `watchlist`, `oportunidades/alertas` |
| JWT vía factoría `createCadenasHandler` | `cadenas/foda`, `cadenas/supply-chain`, `cadenas/value-chain` |
| `Bearer CRON_SECRET` | 10 rutas de `cron/*` + `report/intraday` |
| `Bearer ADMIN_SECRET` | `auth/users` |
| **Ninguno** | **37 rutas** |

Sin protección, entre otras: `scanner-pro` (800 líneas), `oportunidades`,
`analysis`…`analysis7`, `track-record`, `backtest/sore`, `screener`, `sr`,
`heatmap2d`, `triggers/state`, `forecast`, `portfolio/optimize`.

**Escenario de fallo:** `GET /api/scanner-pro` sin cookie. Verificado en runtime:
la petición atraviesa el handler y solo falla al llegar a Supabase (500 por falta de
credenciales locales), nunca devuelve 401. En producción devolvería las señales
completas: gate SORE, estrategia, CSS/DSS/VSS/VRP, niveles S/R y veredicto M7.

**Impacto doble:**
1. Fuga de producto — la propiedad intelectual del sistema queda accesible por URL.
2. Coste — si `valuation_scores` está vacío, `scanner-pro` cae al fallback
   `pool(3, 3s)` contra Yahoo (~100 s, `maxDuration=300`). Sin auth ni rate-limit,
   es un amplificador: peticiones repetidas queman cuota de Yahoo y tiempo de
   función.

**Acción:** aplicar el gate de sesión a los endpoints de cómputo. La vía más limpia
es una factoría equivalente a `createCadenasHandler` — el patrón ya existe y funciona.
Dejar explícitamente públicos solo los que deban serlo, con un comentario que lo diga.

_Corresponde al hallazgo #3 de `AUDITORIA_SORE.md`, que sigue vivo._

### 🟡 MEDIO

#### 2. `parseInt` sin guarda de NaN → respuesta vacía silenciosa

**CONFIRMADO** (reproducido)

`app/api/scanner-pro/route.ts:472-473`

```ts
const limit       = Math.min(parseInt(searchParams.get("limit") ?? "20"), 100);
const minBuyScore = parseInt(searchParams.get("minBuyScore") ?? "50");
```

Reproducción ejecutada:

```
?limit=abc         → Math.min(NaN, 100) = NaN → SP500.slice(0, NaN) = 0 símbolos
?minBuyScore=xyz   → 80 >= NaN = false        → todo filtrado
```

**Escenario de fallo:** `GET /api/scanner-pro?limit=abc` devuelve **200 con `rows: []`**.
El consumidor no distingue "no hay oportunidades hoy" de "mandaste un parámetro
inválido". En un sistema de señales, un vacío silencioso se lee como ausencia de
señal, que es una afirmación.

**Acción:** validar y devolver 400, o caer al valor por defecto explícitamente:

```ts
const parsePositiveInt = (raw: string | null, def: number, max: number) => {
  const n = Number.parseInt(raw ?? "", 10)
  return Number.isFinite(n) && n > 0 ? Math.min(n, max) : def
}
```

#### 3. Login sin límite de tasa

**CONFIRMADO** (lectura de código)

`app/api/auth/login/route.ts` — no hay bloqueo por IP ni por usuario, ni backoff
tras fallos. El coste de bcrypt a 12 rondas (medido: **457 ms**) limita a ~2
intentos/s por conexión, lo que frena un ataque single-thread pero no uno
distribuido o paralelo.

El resto del endpoint está bien resuelto y **no debe tocarse**: hash dummy contra
enumeración por temporización (verificado válido y efectivo), mensaje de error
genérico, cookie `httpOnly` + `sameSite: lax` + `secure` en producción.

**Acción:** contador de intentos fallidos por usuario/IP con bloqueo temporal.

#### 4. Nueve de trece motores de decisión sin ningún test

**CONFIRMADO**

| Con test | Sin test |
|---|---|
| `opportunity`, `analyst-consensus`, `alerts-eval`, `history` | `scoring` (655 líneas), `computeSORE`, `gex7` (568), `gex8`, `portfolio`, `triggers`, `forward`, `optimizer`, `brain` |

36 tests para 59 rutas y ~2 500 líneas de lógica financiera.

**Escenario de fallo:** alguien ajusta un peso en `lib/scoring.ts` o un umbral de
`computeSORE` (45/55/75, `banNakedSells`, hard-blocks de régimen). Las cuatro puertas
siguen verdes y las señales cambian sin que nada lo advierta.

**Acción:** priorizar `computeSORE` y `scoring` con tabla de casos borde. Son los que
producen decisiones directamente.

#### 5. Efectos con dependencias incompletas en `Metodologia1-7`

**CONFIRMADO** (lint)

7 errores `react-hooks/set-state-in-effect` + 7 warnings `exhaustive-deps`, el mismo
patrón replicado siete veces. Ejemplo en `components/Metodologia1.tsx:75-79`:

```tsx
useEffect(() => {
  if (analyzeKey > 0 && ticker) fetchAnalysis(ticker, expiration);
}, [analyzeKey]);   // faltan ticker, expiration, fetchAnalysis
```

**Escenario de fallo:** el usuario cambia `ticker` o `expiration` sin que
`analyzeKey` cambie → el efecto no se redispara, o se dispara con los valores
capturados en el render anterior → **la pantalla muestra el análisis de otro ticker**.
Que sea el mismo patrón en los siete componentes sugiere copia, no decisión.

**Acción:** incluir las dependencias reales, o derivar la clave de disparo de los
tres valores para que el intento sea explícito.

## Descartados tras verificación adversarial

Se investigaron y **no son bugs**. Se documentan para que no se vuelvan a levantar:

| Sospecha | Por qué no lo es |
|---|---|
| `Math.max(...)` sin guarda (5 sitios) | Todos protegidos: `iv:29` corta si `history.length < 5`; `sr:127` exige `or.length >= 3`; `gex7:227` opera sobre clusters creados siempre con ≥1 miembro; `gamma-map:154` y `empresa:378` tienen guarda explícita |
| `auth/users` sin autenticación | Falso positivo de grep. Usa `Bearer ADMIN_SECRET` y **falla cerrado** si la variable no está definida (`route.ts:14`) |
| `cadenas/*` sin autenticación | Falso positivo. La auth vive en la factoría compartida |
| `DUMMY_HASH` inválido rompería el login | Es bcrypt válido (60 chars, prefijo `$2b$12$`). Medido: 457 ms contra el dummy vs 469 ms contra un hash real → la protección temporal funciona |
| Crons huérfanos | Los 5 workflows cubren 10 de los 11 handlers. El único no invocado es `cron/status`, que es endpoint de consulta, no job |
| Secretos filtrados al cliente | Solo `NEXT_PUBLIC_BASE_URL`, `NEXT_PUBLIC_SUPABASE_URL` y `NEXT_PUBLIC_SUPABASE_ANON_KEY`, todas legítimamente públicas. Ningún componente cliente referencia variables de servidor |

## Limitaciones de este QA

Dicho explícitamente para que nadie lea más certeza de la que hay:

1. **No existe `.env.local`.** Ningún endpoint que toque Supabase se pudo ejercitar
   con datos reales. Los 500 de `scanner-pro` y `oportunidades` son por credenciales
   ausentes, no por bugs. La lógica que depende de datos de BD (SORE completo,
   Motor de Oportunidades, triggers) **no se ejecutó**.
2. **No se inspeccionó la base de datos**: migraciones aplicadas, estado de
   `cron_runs`, antigüedad real de `valuation_scores` y volumen de
   `methodology_snapshots` quedan sin verificar.
3. **No hubo revisión visual.** No se comprobó ninguna pantalla renderizada ni el
   modo claro.
4. **El árbol está sucio**: ~60 archivos modificados sin commitear. Este QA describe
   ese estado de trabajo, no lo que hay en `main`.

## Prioridades

1. **Proteger los endpoints de cómputo** (#1) — es el único hallazgo con impacto de
   producto y de coste a la vez, y la factoría a reutilizar ya existe.
2. **Validar parámetros de query** (#2) — arreglo de diez líneas que elimina una
   clase entera de vacíos engañosos.
3. **Tests de `computeSORE` y `scoring`** (#4) — sin esto, cualquier ajuste de
   coeficiente es un cambio a ciegas.
4. **Dependencias de los efectos en `Metodologia*`** (#5) — puede estar mostrando
   datos de otro ticker ahora mismo.
5. Rate-limit de login (#3), retirar `/api/debug` (#6), 400 en `/api/search` (#7).
