## 🔴 CRÍTICO

### 1. Los dos fixes de hoy están en Production pero no en git — el próximo `git push` a `main` los revierte

**Archivos:** `app/api/cron/snapshot/route.ts`, `app/api/auth/users/route.ts`

**Qué pasa:** ambos fixes de esta sesión (propagar `internalAuthHeaders()` en el cron
de snapshot, y el endpoint `PATCH` para cambiar contraseña) se desplegaron a
Production con `vercel deploy --prod` desde el CLI — ese comando empaqueta el
working tree local directamente, sin pasar por git. Confirmé que el proyecto `wall`
en Vercel **sí tiene integración de Git activa** con la rama `main`
(`vercel inspect` de un deployment anterior expone el alias
`wall-git-main-danielinmonrero12345-7487s-projects.vercel.app`, que solo existe
cuando el proyecto está conectado a un repo).

**Escenario de fallo concreto:** en cualquier sesión futura (tuya o mía) se hace
`git push origin main` de un cambio no relacionado con esto → Vercel detecta el push
y dispara un deploy automático **desde ese commit**, que no incluye los dos archivos
de arriba → Production vuelve a la versión rota: el cron `snapshot_daily` vuelve a
fallar en silencio en `macro | sectors | scannerPro` (401 sin auth propagada), y el
endpoint `PATCH /api/auth/users` deja de existir (404), sin ningún error visible que
lo delate hasta que alguien intente cambiar la contraseña o revise `cron_runs`.

**Impacto:** alto — es exactamente el mismo modo de fallo silencioso que originó
toda esta sesión, y quedaría listo para repetirse con el primer push normal.

**Acción recomendada:** commitear y pushear estos dos archivos cuanto antes, antes de
cualquier otro cambio al repo. No lo hice yo porque commitear/pushear no estaba
pedido en esta auditoría — lo dejo señalado en vez de actuar por mi cuenta.

### 3. `/api/auth/users` (POST y PATCH) sin rate-limiting — mitigado por diseño, dejado explícito

A diferencia de `/api/auth/login` (que sí usa `comprobarLimite`/`registrarFallo`),
ni el `POST` preexistente ni el `PATCH` nuevo de `app/api/auth/users/route.ts` tienen
límite de intentos. Mitigante: ambos exigen `Bearer ADMIN_SECRET` (secreto de alta
entropía, no una contraseña de usuario adivinable), así que fuerza bruta no es
práctica. El `PATCH` nuevo **no** introduce una superficie nueva respecto al `POST`
ya aceptado: cualquiera con el `ADMIN_SECRET` puede cambiar la contraseña de
**cualquier** usuario con solo conocer su `username` — mismo modelo de confianza
"admin único controla todo", consistente con que la tabla tiene un solo usuario hoy.
Lo señalo explícito porque el usuario lo pidió verificar, no porque sea una
regresión nueva.
